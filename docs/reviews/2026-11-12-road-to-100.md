## 3. Why the number has stalled

1. **The rating is an estimate, not a measurement.** 89 components sit at
   exactly 80, 85 or 90% (61 KB of gap). 150 components have been rated
   once, on 10-21, and never audited routine by routine (61 KB of gap).
2. **Many listed gaps are stale.** In about half of the last 16 lanes the
   backlog premise was wrong: the code was already ported and live. Audits
   alone moved SG_CharacterAI from 46% to 88% and FLX_Character_Motions
   from 66% to 80%.
3. **Part of the gap can never be ported.** Components carry gaps for GL
   plumbing that wgpu replaces, threads that Bevy replaces, code no path in
   0.9.5 reaches, and deviations kept on purpose (the supersample jitter,
   the path planner's shared stamp table). Under the current rules these
   stay below 100% for ever.
4. **Lanes rate their own work**, so ratings drift up without a second
   check, and the remaining text gaps are not comparable between lanes.

A rough keyword sort of the latest gap texts, weighted by gap bytes:
30% name something missing or partial, 14% are ported but have no caller,
9% are engine-replaced, 3% unreachable, 3% belong to the character creator,
and 39% have no gap text at all.

## 4. What 100% should mean

Two separate goals, each with its own measure.

**A. Code coverage: every function accounted for.** A ledger with one row
for each of the 8,783 functions. Each row ends in exactly one state:

| state | proof required |
|---|---|
| live | the Rust item that ports it, and a live caller |
| engine-replaced | what replaces it, and that the visible behaviour matches |
| unreachable in 0.9.5 | the caller analysis that shows no path reaches it |
| not applicable | unused runtime library or dormant editor |
| kept deviation | the decision and its reason, approved by the owner |

100% means no row is left as missing, uncalled, partial or unknown.
Coverage is then computed from the ledger's bytes, not from estimates.

**B. Behaviour: the game plays and looks like the original.** Code
coverage does not prove this. It needs its own evidence: retail
side-by-side scenes, lockstep traces, and full playthroughs.

## 5. Plan

### Phase A — Build the function ledger (measure first)

1. Generate the ledger skeleton from the function list (address ranges,
   bytes, component), kept in `context/` with the other analysis data.
2. Fill it from what exists: the routine tables of rounds 130–202, the
   component evidence, and an automated caller pass over the disassembly
   (functions with no path from the entry point, a virtual table or a
   registered callback are unreachable candidates).
3. Run read-only audit lanes, one per section (16 sections, about 20
   lanes, 8–10 at a time), to resolve every row that is still unknown.
   Each lane ends with a table, not code.
4. A second agent reviews each lane's table against the assembly before it
   is accepted. Ratings no longer come from the lane that did the work.
5. Change `recalc_coverage.py` to compute from the ledger.

Result: the true coverage number, and an exact work list ordered by bytes.
Expect the reimplemented share to rise noticeably from audit alone.

### Phase B — Close the ledger, class by class

1. **Ported but uncalled** (at least 44 KB): for each, find the original
   caller and wire it, or prove it unreachable. Cheapest gains.
2. **Missing and reachable**: port in byte order, one component family per
   lane, with the existing round checks.
3. **Engine-replaced**: move out of "partial" with evidence that the
   picture, timing or values match (for example the GL program binders,
   the kd-tree builder thread, the deferred-call ring).
4. **Unreachable**: document with the caller proof and close.
5. **Owner decisions** (section 6).

Open leads to take first, because they are possible bugs:
- the save and checkpoint slot kinds may be swapped;
- a level-exit save keeps the old level's position;
- the Control Mind end still writes frame state over newer steps.

### Phase C — Behavioural fidelity

1. **Retail reference set.** Only 8 retail references exist. Capture about
   50 scenes with the retail camera tool: every level type, the menus, the
   inventory, the power screen, combat, each power, weather.
2. **Outdoor comparisons.** Add a debug seed for the sun and weather;
   outdoor shots cannot be compared today.
3. **Scenario matrix.** Extend the feature sweep (80 scenes) so every
   ledger family has at least one scene that reaches it in the game. Many
   new paths are proved by unit tests only.
4. **Playthroughs.** Story from the first level to the last, an arena
   career, save and continue, and loading retail saves read-only.
5. **Free mode.** The write-conflict sweep must come back clean in every
   scene, not only lockstep.

### Phase D — Finish

Performance on a loaded scene, settings, gamepad, packaging, and a
regression suite of recorded inputs (Phase 8 of `docs/PLAN.md`).

### Working rules to change

- Rate from the ledger, reviewed by a second agent.
- Queue GPU grid runs: three lanes at once ran the 3090 out of memory
  several times.
- Keep the last three round binaries while lanes compare against them.
- Audit before porting: verify a backlog premise against the assembly
  before any code is written.

## 6. Decisions for the owner

1. **The definition in section 4.** Without closing states for
   engine-replaced and unreachable code, 100% cannot be reached.
2. **Steam.** Steam API glue is at 7% and Steam Input at 75%; Steam is not
   linked. Either link Steamworks or close these as a kept deviation.
3. **Character creator.** About 9 KB of gap (SG_CharacterGen,
   SG_Character_Create, TCharCreation) belongs to the other session.
4. **Composite terrain draw.** It stays opt-in until a retail outdoor
   reference exists.
5. **Kept deviations.** Confirm the ones made so far (supersample jitter,
   shared stamp table, platform items such as the screen-saver refusal).

## 7. Order of work

1. Phase A, ledger and audits.
2. The three open leads.
3. Phase B.1 and B.3–B.4 (wiring, reclassifying, closing): fast, low risk.
4. Phase B.2 (real ports) in byte order, with Phase C.1–C.2 in parallel.
5. Phase C.3–C.5, then Phase D.

No time estimate is given for Phase B: its size is only known once the
ledger exists.
